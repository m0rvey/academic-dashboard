# Архитектурный аудит Academic Dashboard

**Аналитик:** Senior Python Architect / Lead System Auditor (Deepseek)
**Дата:** 2026-06-09
**Версия кода:** 1.0.0
**Объём кодовой базы:** ~6 200 строк Python

---

## 1. Резюме

Academic Dashboard — персональный планировщик учебной нагрузки для студента,
реализованный на Python 3.10+ с тремя интерфейсами: **Flet GUI** (десктоп),
**Telegram Bot** (Aiogram 3) и **CLI**. Проект демонстрирует surprisingly высокое
качество для студенческого pet-проекта: чистая 3-слойная архитектура,
нормализованная схема БД 3НФ с миграциями, Pydantic-валидация,
fail-closed аутентификация, 44 теста. Однако аудит выявил ряд проблем —
от критических (живой токен в репозитории) до архитектурных (дублирование
логики приоритета, O(N)-операции в Python вместо SQL).

**Общая оценка: 6.5/10** — рабочий продукт с хорошей архитектурной базой,
требующий доработок в безопасности, производительности и тестовом покрытии.

## 2. Архитектурный анализ

### 2.1. Слои и модули

Проект следует **трёхслойной архитектуре**:

```
┌─────────────────────────────────────────────────────┐
│  Presentation Layer (UI, CLI, Telegram Bot)          │
│  src/ui/  |  main.py (CLI)  |  src/bot/handlers/    │
├─────────────────────────────────────────────────────┤
│  Core Layer (Business Logic, Models, Database)       │
│  src/core/{logic,database,models,nlp_parser,...}.py  │
├─────────────────────────────────────────────────────┤
│  Data Layer (SQLite WAL)                             │
│  data/planner.db                                     │
└─────────────────────────────────────────────────────┘
```

**Плюсы:**
- Чёткое разделение ответственности: `src/core/` не импортирует из `src/ui/` или `src/bot/`
- Презентационные слои изолированы друг от друга — можно добавлять новые UI
- DatabaseManager выступает Repository, инкапсулируя SQL

**Минусы:**
- **Global singleton `db`** в `src/bot/dependencies.py:22` — модуль-глобал,
  затрудняющий юнит-тестирование (тесты вынуждены мутировать ALLOWED_USERS
  в `test_bot_auth.py:12-14` как side effect)
- **DatabaseManager не зависит от абстракции** — нет интерфейса/ABC,
  что мешает подмене БД для тестов (хотя conftest с `tmp_path` решает
  проблему изоляции)
- **`core/config.py` импортируется циклически** через `models.py:46-48` —
  импорт спрятан внутрь `field_validator`, что работает, но хрупко

### 2.2. Схема БД и миграции

**Схема (3НФ):**

```
tasks (id, subject, description, deadline, effort_score, status, grade)
  ↕ M:N ↕
task_tags (task_id → tasks.id CASCADE, tag_id → tags.id CASCADE)
  ↑     ↑
tags (id, name UNIQUE)
```

**История миграций v0→v4** в `migrations.py` — качественная, идемпотентная,
с обработкой краевых случаев (v4 чинит битый FK после v3). Единственный
недостаток: миграция v3 с `ALTER TABLE ... RENAME TO` + `DROP` —
деструктивная операция для production (но для локального SQLite —
приемлемо). **Нет индексов** на `deadline`, `status`, `subject` — на 500+
задачах запросы начнут замедляться.

### 2.3. Шаблоны проектирования

| Паттерн | Реализация | Оценка |
|---------|-----------|--------|
| **Repository** | `DatabaseManager` как CRUD-прослойка | ✅ |
| **Singleton** | `db`, `bot` в `dependencies.py` | ⚠️ Module-level global |
| **State / FSM** | Aiogram StatesGroup для wizard | ✅ |
| **Middleware** | AuthMiddleware для Aiogram | ✅ |
| **Observer** | watchdog `DBChangeHandler` | ✅ |
| **Component** | OOP `TaskCard` для Flet | ✅ |
| **Lazy Loading** | AppState.dirty_tabs + "Load More" (30 items) | ✅ |
| **Debounce** | call_later 300ms для watchdog | ✅ |

## 3. Анализ производительности

### 3.1. База данных

**Проблема: O(N) расчёт high_priority**
`database.py:573-580` — после SQL-запроса загружает все активные задачи,
для каждой вызывает `calculate_priority` в Python-цикле:

```python
for r in active_rows:
    t = self._row_to_task(r, tags_map.get(r["id"], []))
    if calculate_priority(t) >= 2.5:
        high_priority_count += 1
```

**Решение:** Перенести условие `priority >= 2.5` в SQL (формула уже
продублирована в `database.py:465-479` для сортировки).

**Проблема: Дублирование формулы приоритета**
Формула `P = effort / (days_left + 1) * exam_multiplier` реализована:
1. В Python: `logic.py:25`
2. В SQL: `database.py:465-479`

Это **DRY violation**, accepted для производительности. Однако при изменении
формулы нужно менять в двух местах.

**Проблема: Нет индексов**
Индексы на `tasks.deadline`, `tasks.status`, `tasks.subject` отсутствуют.
Для локальной БД (<1000 задач) это не критично, но:
- `get_kpi_stats` сканирует всю таблицу для `SUM(CASE WHEN ...)`
- `get_filtered_tasks` с сортировкой по дедлайну — full scan
- `get_daily_load_for_date` — lookup по `deadline` без индекса

### 3.2. Flet GUI

- **Полный ререндер DOM** при каждом обновлении — Flet не использует Virtual DOM
- Пагинация 30 задач + lazy-обновление вкладок **частично** решают проблему
- `subject_colors` в `views.py:71-80` — **мутируемый кэш**, растущий
  неограниченно при появлении новых предметов (но это O(N) с N = кол-во
  уникальных предметов, а не задач — практически незначимо)

### 3.3. Telegram Bot

- `get_all_tasks()` вызывается в каждом хендлере (`commands.py:70`,
  `tasks.py:34,256,331`) — загрузка всех задач из SQLite в память
  при каждом запросе
- **Нет кэширования** на уровне бота (в отличие от GUI с AppState)
- `handle_natural_language_message` срабатывает на **каждое** некомандное
  сообщение — проверка состояния FSM внутри хендлера, а не через фильтр

## 4. Анализ безопасности

### 4.2. ВЫСОКИЕ

#### SQL Injection
**Полностью отсутствует** — все запросы через параметризованные `?`.

#### XSS в Telegram Bot
Пользовательский контент рендерится с `parse_mode="Markdown"`.
Нет экранирования Markdown-спецсимволов (`_`, `*`, `` ` ``, `[`).
Если пользователь введёт описание с синтаксисом Markdown, он будет
интерпретирован. **Атака маловероятна** (single-user бот с whitelist),
но при расширении аудитории станет проблемой.

#### Rate Limiting
**Отсутствует.** Хендлеры бота не ограничивают частоту запросов.
Если токен будет скомпрометирован, злоумышленник может:
- Заспамить `/add` (DDOS на SQLite)
- Выкачать всю БД через `/backup`
- Импортировать большую `.db` через `handle_document_restore`

### 4.3. СРЕДНИЕ

#### Экспозиция путей ФС
`/backup` отправляет пользователю файл `planner.db` — любой, у кого есть
доступ к боту, получает полную копию данных (со списком всех задач,
оценками, пользователями).

#### Небезопасное удаление WAL
`files.py:69-70` — удаляет WAL/SHM файлы через `unlink`. Если по какой-то
причине БД ещё открыта (race condition), это может привести к повреждению.

### 4.4. НИЗКИЕ

- `except Exception: pass` в `dashboards.py:67` — скрывает ошибки
- Incorrect `_get_tags_for_tasks` signal in `dashboards.py:67` — bare except

## 5. Качество кода

### 5.1. Сильные стороны

- **Pydantic v2 валидация** — модели с `field_validator` и `validate_assignment`
- **SQLite WAL mode** — корректная настройка для конкурентного доступа
- **Идемпотентные миграции** — `CREATE TABLE IF NOT EXISTS`, проверка версий
- **Orphan cleanup** — `DELETE FROM tags WHERE id NOT IN (SELECT DISTINCT tag_id FROM task_tags)`

## 6. Детальный анализ компонентов

### 6.1. NLP Parser (`nlp_parser.py`, 292 строки)

**Реализация:** Regex-based, русскоязычный.

**SUBJECTS_MAP** — маппинг ~22 предметов с учётом падежей и сленга:
- `"матан"` → `"Математика"`, `"инфа"` → `"Информатика"`
- Качественно покрывает школьную программу

**Даты:** обрабатывает 5+ форматов:
- "на завтра", "сегодня", "послезавтра"
- "через N дней", "через неделю"
- "до конца недели", "в следующую среду"
- Явный формат YYYY-MM-DD

**Effort score:** извлекается из текста с умным исключением дат (не путает
числа внутри YYYY-MM-DD с effort_score).

**Проблема:** Парсер **нестабилен** при сложных предложениях. Регулярные
выражения конкурируют и перезаписывают `text_cleaned` — порядок извлечения
важен и хрупок. При изменении текста после извлечения одних данных могут
сломаться другие извлечения.

**Пример проблемы:** `"история 4 класс 4"` (тест `test_parse_nlp_mangled_numbers`)
— парсер возвращает правильный результат, но это случайность: алгоритм
выбирает последнее число в диапазоне 1-10, что может ошибаться.

### 6.2. GPА Calculator (`grade_calculator.py`, 28 строк)

**Математически корректен.** Решение уравнения в замкнутой форме:

```
k = ceil((target * n - current_sum) / (planned_grade - target))
```

O(1), аналитическое, без итераций. **Excellent.**

### 6.3. Config (`config.py`, 25 строк)

Чистый модуль констант. Единственный недостаток — `DB_PATH` вычисляется
через `Path(__file__).resolve().parent.parent.parent` — ломается при
запуске не из корня проекта (но решается `main.py:7`).

## 7. Специфические проблемы Flet

- **Flet 0.25.2** — относительно зрелая версия, но экосистема быстро
  меняется. Зависимость `flet==0.25.2` (строгая) требует обновления
  вручную.
- `ft.app(target=main)` блокирует поток — watchdog работает в отдельном
  потоке, но `page.run_task()` и `asyncio.to_thread()` — костыли,
  указывающие на ограничения Flet.
- `page.update()` — полный ререндер; нет инкрементального DOM.
- **Нет обработки reconnection** — если БД удалена во время работы GUI,
  приложение упадёт с `sqlite3.OperationalError`.
